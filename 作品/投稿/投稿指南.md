# 组员投稿指南（给 AI 执行）

本文写给帮组员整理投稿的 AI，例如驱动 DeepSeek 的编码助手。组员本人也可以照着做。

## 0. 先读这些，别的不用读

- 本文件。
- [经验库](经验库.md)：开工前看“固定做法”和“已知坑”，投稿时说明借鉴了哪条。
- 选题时可看[精选场景库](../../docs/curricula/scene-library/README.md)，拿到场景编号（如 `CA-010`）。
- 做公式动画时可参考[公式动画创作引导](../../docs/公式动画创作引导.md)。

投稿不走仓库原生制作链。**不要读 `ai/` 下的完整规则，也不要改投稿目录以外的任何文件。** `经验库.md` 由维护者统一更新，投稿 PR 不要改它，想入库的做法写在你自己的 `制作记录.md` 里。

## 1. 投稿要交什么

一次投稿对应一条作品（一个主题），放在一个独立目录。成片只交一份，制作过程也要交：做过什么、改进了什么、还剩哪些问题。这样别人能直接拿去用，也知道哪里还要注意。

```text
作品/投稿/<投稿id>/
  投稿.json        必需：机器可读的登记（片名、场景、工具、视频链接与 SHA256、状态）
  制作记录.md      必需：目标、成片、制作过程、优化了什么、未解决的问题、可复用做法
  源码/            建议：能重新渲染的场景代码和配置，最好附渲染命令
  提示词/          建议：给 DeepSeek 的关键提示词，以及关键回复的摘录
  截图/            建议：问题和改进前后的关键帧，不超过 12 张
  讲稿.md          有配音时必需：最终讲稿全文
```

**视频本身不进 Git。** MP4 上传到本仓库 GitHub Release（见第 4 节），Git 里只登记链接和 SHA256；`.gitignore` 已忽略 `*.mp4`、`*.mov`、`*.wav`、`*.mp3`、`*.srt`、`*.ass`。

入库限制由检查脚本执行：
- 只收文本、代码和图片（`.md .json .py .txt .csv .yml .yaml .toml .cfg .tex .html .css .js .svg .png .jpg .jpeg .gif .webp`）。
- 单个文件不超过 2 MB，整个投稿不超过 10 MB。
- 不收 `.DS_Store`、`._*` 和符号链接。
- 不得出现 API Key、Token、私钥、带密码的 URL、内网地址或个人主机路径（如 `/Users/某人/`、`C:\Users\某人\`）。日志和报错里的路径改写成 `~` 或相对路径。

## 2. 投稿 id 与目录名

格式为 `YYYYMMDD-作者-主题`，只用小写字母、数字和连字符。日期取第一次投稿的日期，作者是 GitHub 用户名的小写形式（用户名本身带连字符就照原样保留），主题用英文短词。

例：`20261126-pengweitaing-accumulation-rate`。目录名和 `投稿.json` 里的 `id` 必须相同，视频附件名也由它生成。

## 3. 执行步骤

**Windows**：下面所有命令都在 Git Bash 里运行（安装 Git for Windows 时自带），不要用 PowerShell 或 cmd。`python3` 不可用时改用 `python` 或 `py -3`。JSON 和 Markdown 都存成 UTF-8。

先设好变量，后面的命令直接引用，不要把 `<...>` 原样粘进命令：

```bash
REPO=gduf-community/ManiMind
GH_USER=<GitHub 用户名，原样>
ID=<投稿 id，见第 2 节>
VER=<最终版本号，如 v003>
VIDEO=<本地最终 MP4 的完整路径>
TMP=$(mktemp -d)        # 仓库外的临时目录，放改名后的视频和 PR 正文
```

0. **前置检查**，任一项不通过就先告诉组员：
   - `python3 --version` 为 3.9 及以上。
   - `git config user.name`、`git config user.email` 都有值。
   - `gh auth status` 已登录组员本人的账号。
   - `ffprobe -version` 可用；装过 manim 的电脑通常已有 ffmpeg，有时只在 manim 虚拟环境的 `bin/`（Windows 为 `Scripts\`）里。没有的话，从 ffmpeg 官网下载，或请组员在播放器的“媒体信息”里读出时长和分辨率告诉你。
1. **向组员问清并收集材料**：
   - 片名、场景编号（没有就写 null），GitHub 用户名，最终 MP4 路径。
   - 谁完整看过、怎么看的（几倍速、有没有听声音）。
   - 各版本的问题清单，带视频时刻；每版改了什么、改完是否复查过。你看不了视频，**时刻、分段和“改好了没有”只能来自组员或他们留下的记录**。
   - 制作过程的原始材料：和 DeepSeek 的对话、各版本源码、渲染日志。网页对话看不到的，请组员导出或复制给你。
   - **材料里没有的事不写。** 拿不到的就写“组员未提供”，不要替组员编造“看过”“改好了”。
2. 同步并开分支：
   ```bash
   git switch develop && git pull
   git switch -c "submit/$GH_USER-<主题>"
   ```
3. 复制模板：`cp -R 作品/投稿/_模板 "作品/投稿/$ID"`，用不到的子目录整个删掉。
4. 填 `投稿.json`（字段见第 5 节），写 `制作记录.md`（第 6 节），替换全部“【待填】”，删掉注释里的样例。
5. 放入源码、提示词、截图。截图命名为 `v002-0213.png`，即“版本-分秒”。
6. **上传视频前先向组员确认**：文件对不对、版本号、要上传到 `gduf-community/ManiMind` 的公开 Release。确认后按第 4 节上传，并回填 `url`。
7. 自检，必须看到“通过”：
   ```bash
   python3 scripts/check_submissions.py "作品/投稿/$ID" --video "$VIDEO" --online
   ```
   - 脚本只用 Python 标准库，不需要装 manim。
   - 还没上传时去掉 `--online`。这时 `url` 为空，会出现一条“提醒”，属于预期，不算失败，但要在 PR 里说明视频还没上传。
   - 脚本只查格式和明显错误，“通过”不代表内容正确，也不代表你核对过记录。
8. **提交前请组员通读 `制作记录.md` 并确认属实。** 组员没核对，就把记录人写成“DeepSeek 整理，组员未核对”。得到同意后再提交、推送并开 PR：
   ```bash
   git add "作品/投稿/$ID"
   git commit -m "投稿：<中文片名>（$GH_USER）"
   git push -u origin HEAD
   gh pr create --repo "$REPO" --base develop --title "投稿：<中文片名>（$GH_USER）" --body-file "$TMP/pr.md"
   ```
   - PR 正文按第 8 节模板写进 `$TMP/pr.md`，不要放进仓库。
   - PR 只包含这一个投稿目录。
   - 还在做（`status` 为 `draft`）也可以先开，加 `--draft`，用来求助或交流；要等改成 `self_checked` 才合并。
   - **`git push` 报没有权限**时，说明账号没有 Write 权限，改走 fork：
     ```bash
     gh repo fork "$REPO" --remote --remote-name fork
     git push -u fork HEAD
     gh pr create --repo "$REPO" --base develop --head "$GH_USER:$(git branch --show-current)" --title "投稿：<中文片名>（$GH_USER）" --body-file "$TMP/pr.md"
     ```

## 4. 上传视频到 Release

所有投稿视频都传到同一个预发布 [`submissions`](https://github.com/gduf-community/ManiMind/releases/tag/submissions)（维护者已建好，不要再新建 Release）。附件名为 `<投稿id>-<版本>.mp4`；投稿 id 以日期开头，所以不需要按月份分开。显示名用中文片名。

```bash
cp "$VIDEO" "$TMP/$ID-$VER.mp4"             # 在仓库外改名，不在仓库里留大文件
gh release upload submissions "$TMP/$ID-$VER.mp4#<中文片名> $VER" --repo "$REPO"
```

- 链接为 `https://github.com/gduf-community/ManiMind/releases/download/submissions/<投稿id>-<版本>.mp4`。脚本会核对这个链接。
- 报 `release not found`，就停下来告诉组员，由维护者处理；不要自己创建 Release，以免影响 `videos-20261104` 正式合集的“Latest”标记。
- **不要用 `--clobber` 覆盖已有附件。** 改了视频就升一个版本号重新上传，旧版保留。
- 上传报 403 或没有权限，说明组员账号没有 Write 权限。这时 `url` 留 `null`，状态照常填写，在 PR 里说明视频怎么交给维护者，由维护者代传后补链接。不要把网盘链接写进仓库。
- 建议 1080p、30fps，H.264 编码的 MP4。

需要的数值（直接得到纯数字，填进 JSON 时不要加引号）：

```bash
shasum -a 256 "$VIDEO" | cut -d' ' -f1                                    # sha256（Git Bash、Linux 用 sha256sum）
wc -c < "$VIDEO" | tr -d ' '                                               # size_bytes
ffprobe -v error -show_entries format=duration -of csv=p=0 "$VIDEO"        # duration_seconds
ffprobe -v error -select_streams v:0 -show_entries stream=width,height -of csv=s=x:p=0 "$VIDEO"   # resolution
```

## 5. `投稿.json` 字段

| 字段 | 写法 |
| --- | --- |
| `schema_version` | 固定为 `1` |
| `id` | 与目录名相同 |
| `title` | 中文片名 |
| `subject` | `高中数学`、`高中物理`、`微积分`、`线性代数`、`概率论`、`数理统计`、`其他` 之一 |
| `scene_id` | 场景库编号，如 `"CA-010"`；不对应任何场景时写 `null`。脚本会核对编号存在 |
| `author` | `{"github": "用户名", "name": "可选的组内称呼"}` |
| `created_at` | `YYYY-MM-DD`，与目录名的日期一致 |
| `based_on` | 借鉴的经验库编号或其他投稿 id，如 `["EXP-002", "20261120-someone-limits"]`；没有就写 `[]` |
| `tools` | `model`：DeepSeek 型号与模式；`agent`：驱动工具及版本，手动对话也照实写；`renderer`：渲染库及版本；`tts`：配音工具或 `null` |
| `status` | 见下表 |
| `watched_full` | 是否有**人**以 1 倍速把最终版完整看过一遍 |
| `listened_full` | 有配音时，是否有人完整听过一遍；静音片写 `false` |
| `videos` | 每个上传的版本一条。`role` 为 `final`（只能一条）或 `intermediate`；另有 `version`、`url`、`sha256`、`size_bytes`、`duration_seconds`、`resolution`（如 `1920x1080`）、`audio`（`none`/`tts`/`human`）、`captions` |

| `status` | 含义 | 谁来填 |
| --- | --- | --- |
| `draft` | 还在做；可以没看完、没上传 | 作者 |
| `self_checked` | 作者本人以 1 倍速完整看过最终版，记录写完 | 作者 |
| `peer_reviewed` | 另一位没参与制作的组员完整看过，并在 PR 里留了具体意见 | 作者，在评审人留言后填 |
| `adopted` | 维护者决定采纳（进成片区或作为做法证据） | **只由维护者填** |

诚实标注：
- AI 抽帧、看截图、脚本通过、渲染成功，都**不等于**“完整看过”，也不等于内容正确。
- AI 不能替人把 `watched_full` 写成 `true`，必须由组员确认。不确定就写 `false`，并保持 `draft`；不要为了通过检查改状态。
- `draft` 时 `videos` 可以是空列表；只要登记了视频，各字段就要写全。
- 中间版本只上传对说明改进有用的，不必每版都传。

## 6. `制作记录.md` 怎么写

必须有以下六个二级标题，名字一字不差。不能留空（只剩注释也算空）；确实没有内容就写“无”并说明原因。模板注释里以“样例：”开头的文字只是格式示范，必须删掉换成真实内容。

1. **目标**：给谁看，先修是什么，片尾观众应能解释或预测什么。对应场景时，引用场景库里的“出口任务”。
2. **成片**：最终版本号、时长，有无配音字幕，按时间分段的内容。再写谁、怎么看过，例如“作者 1 倍速完整看过；配音未听审”。
3. **制作过程**：按真实顺序写。包括选题，每轮给 DeepSeek 的要求（提示词放 `提示词/` 并在这里引用文件名），渲染了哪些版本，每版看出了什么。**失败的尝试也写**，这对别人最有用。最后写能复现成片的渲染命令。
4. **优化了什么**：用表格写“版本 → 看到的问题（带时刻）→ 怎么改的 → 改完是否真的好了”。最后一栏只写实际看到的结果，没复查就写“未复查”。
5. **未解决的问题**：每条以 `- [ ]` 开头，写版本和时刻、现象、试过什么、猜测的原因。已解决的改成 `- [x]` 并写解决办法。`--list` 会统计未勾选的条数。
6. **可复用做法**：值得别人照搬的做法，每条写做法、适用条件和证据位置（源码里的类或函数名、截图文件）。维护者核实后收进经验库。

可选两节：**借鉴与反馈**，写用了经验库或别人投稿的哪条、效果如何，这是做法能否“固定”的依据；**下一步**，写继续做的话先改什么。

记录人照实写在开头：“组员本人”、“DeepSeek 整理，组员已核对”或“DeepSeek 整理，组员未核对”。只有组员真的通读确认过，才能写“已核对”。

## 7. 改进已有投稿

- **改自己的作品**：在原目录里追加。`videos` 新增一个版本，原 `final` 改为 `intermediate`，新版设为 `final`。`制作记录.md` 的过程和优化表继续往下写，不删旧内容。分支和 PR 另开。
- **改别人的作品**：新建自己的投稿目录，`based_on` 写原投稿 id。在“借鉴与反馈”里说明保留了什么、改了什么、为什么更好。不要改别人的目录。
- **解决了经验库里的未解决问题**：在 `based_on` 写对应的 `Q-编号`，并在“未解决的问题”或“优化了什么”里写清怎么解决的。

## 8. PR 正文模板

```markdown
## 投稿
- 目录：作品/投稿/<投稿id>/
- 成片：<url>（<版本>，<时长>，静音/配音/字幕）
- 谁看过：<例如 作者 1 倍速完整看过一遍；配音未听>

## 这次优化了什么
<最多 3 条，摘自 制作记录.md>

## 还没解决的问题
<摘要；没有就写“无”>

## 建议收进经验库的做法
<摘自“可复用做法”；借鉴了经验库哪条、是否有效>

## 自检
<照实粘贴实际运行的命令和脚本输出；没加 --online 或 --video 要写明>
```

## 9. 取长补短怎么运转（维护者）

1. **审投稿 PR**：跑检查脚本，完整看成片，核对记录与视频是否一致，在 PR 里给出带时刻的意见，再合并。合并不改变作品状态；采纳时由维护者把 `status` 改成 `adopted`。
2. **更新[经验库](经验库.md)**：把“可复用做法”整理成 `EXP-编号`，新条目先放“待验证”，并注明来源投稿。至少两位不同作者的投稿实际用过且有效，维护者看过证据后，再移入“固定做法”。如有相反反馈，补充适用条件或移入“已知坑”。
3. **汇总未解决问题**：反复出现或影响大的问题记为 `Q-编号`，链接到出处，供组员认领。
4. **转为正式成片**：被采纳、需要进[成片区](../成片/README.md)的作品，按[命名与交付](../../docs/命名与交付.md)另行发布并登记[作品目录](../目录.json)。投稿区原记录保留不动。

查看全部投稿：`python3 scripts/check_submissions.py --list`，会按场景分组，同一场景的不同做法放在一起比较。
